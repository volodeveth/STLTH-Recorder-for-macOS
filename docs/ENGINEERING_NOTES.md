# Інженерні нотатки: STLTH Recorder for macOS

Документ про **розвилки і рішення**, а не про код. Тут те, що не видно з
репозиторію: які були варіанти, чому обрано цей, і чого це коштувало.

> 🚧 — розділи, що заповнюються фактами по ходу задач (позначені задачею).

---

## 1. Як захоплювати системний звук

Три реальні варіанти на macOS 14.4+:

| Підхід | Суть | Чому не він |
|---|---|---|
| **A. Global process tap** | `CATapDescription(stereoGlobalTapButExcludeProcesses:)` — мікс усього системного виводу, крім власного процесу | **обрано** |
| B. Per-process taps | Тапати конкретні процеси Zoom / Chrome | Потребує discovery і трекінгу аудіопроцесів (у Chrome звук грає окремий utility-процес), ламається при перезапуску процесу, **не покриває живу зустріч у кабінеті** (вимога F-1). Виграш — косметично чистіший канал; ризики реальні |
| C. ScreenCaptureKit audio | Захоплення аудіо через API запису екрана | TCC-дозвіл виглядає для користувача як «запис екрана» (лякає в розмові про особисті фінанси), вмикає системний індикатор запису екрана. ТЗ прямо вказує на Core Audio taps |

**Наслідок обраного підходу, який чесно фіксуємо:** у системний канал потрапляють
сторонні звуки (нотифікації, музика). Рекомендація в README — Focus mode під час
зустрічі. Альтернатива (per-process) коштувала б надійності на живих зустрічах.

## 2. Синхронність каналів: за побудовою, а не корекцією

Вимога ТЗ (критерій №1): розбіжність каналів < 300 мс за 60 хвилин.

Наївне рішення — два незалежні потоки (мікрофон окремо, tap окремо) і зшивання
за таймстемпами. Проблема: два різні аудіопристрої мають **різні годинники**,
які повільно розходяться. За 60 хвилин це дає накопичувальний дрейф, і його
доводиться вимірювати й компенсувати постфактум.

**Рішення:** tap і мікрофон додаються в **один aggregate device**. Один пристрій →
один IO-колбек → один годинник. Дрейф між каналами не виникає в принципі;
`kAudioSubDeviceDriftCompensationKey` бере на себе розбіжність між фізичними
під-пристроями всередині aggregate.

Це головна причина, чому вимога №1 закривається архітектурою, а не хитрощами.

**Виміряно на залізі (08.08), рівно 60 хвилин:**

| Показник | Значення |
|---|---|
| Довжини треків | 172 801 169 семплів обидва, різниця **0.0 мс** |
| Кліків знайдено | 720 з 720 в обох каналах |
| **Дрейф каналів** | **+6.4 мс/год (95% ДІ ±0.3)** |
| Вимога ТЗ | < 300 мс за 60 хв → **запас у ~47 разів** |

Зверни увагу на довірчий інтервал: він тут важливіший за саме число. На
70-секундному прогоні та сама регресія давала −14.5 ± 117 мс/год — формально
«пройдено», фактично нічого не доведено. Година бази стиснула інтервал у ~390
разів, і лише тоді дрейф став **виміряною величиною**, а не відсутністю сигналу.
Деталі — `docs/notes/drift-report.md`, повний покліковий розклад —
`docs/notes/evidence/drift-2channel-60min.md`.

## 3. Інваріант таймлайна: тиша пишеться, а не вирізається

Вимога ТЗ (критерій №4): 10 хвилин mute не зсувають таймлайн.

Якщо просто дописувати в файл ті буфери, що прийшли, будь-який розрив потоку
(зміна пристрою, глюк CoreAudio, sleep) робить файл **коротшим** за сесію — і
канали розʼїжджаються тим сильніше, чим більше розривів.

**Інваріант:** у кожному файлі кількість семплів = тривалість сесії × 48000,
завжди. Кожен буфер звіряється з очікуваним таймстемпом; розрив заповнюється
тишею (`TimelineAccountant`, `RecorderCore`). Джитер < 5 мс не вважається розривом.

Це той самий механізм, що закриває і критерій №4, і відновлення після збоїв.

## 3a. Баг, який знайшов реальний `kill -9`, а не теорія

Спека обіцяла: «файли писались потоково — аудіо ціле». Ми це **перевірили**: обірвали
19-хвилинний запис через `kill -9` і спробували прочитати файли.

Аудіо справді вціліло — але виявилась пастка. Поки CAF пишеться, його `data`-chunk
несе розмір **−1 («невідома довжина»)**; справжній розмір `AVAudioFile` дописує лише
при коректному закритті. `kill -9` цей крок пропускає, і далі виходить асиметрія:

| Читач | Результат |
|---|---|
| QuickTime, `afplay`, `AVAudioFile` | ✅ читають (Apple-стек толерантний до −1) |
| libsndfile, ffmpeg | ❌ `file is malformed` |

Формально критерій №6 («файли читаються плеєром») виконувався б і так. Але записи
призначені для аналітичного пайплайну STLTH, а він майже напевно на ffmpeg — тобто
після падіння застосунку сесія дійшла б до платформи «зіпсованою».

**Рішення:** `CAFRepair` при відновленні сесії дописує справжній розмір
`data`-chunk (`розмір_файлу − offset`), не торкаючись жодного семпла. Операція
ідемпотентна, тож лікує і сесії, перервані попередніми версіями.

Перевірено на тому самому реальному 19-хвилинному файлі:

```
ДО:    data ffff ffff ffff ffff   → libsndfile: "file is malformed"
ПІСЛЯ: data 0000 0000 069d 9004   → libsndfile: 55 494 656 фреймів
```

Мораль, яку варто зафіксувати: «файли пишуться потоково» — це ще не «файли
переживають краш». Різницю видно лише тоді, коли справді вбиваєш процес.

## 3b. Висновок, який довелося спростувати (і чому це важливо)

07.08 стенд показав, що aggregate з мікрофоном не дає жодного IO-колбека. Проба
шести розкладок (`Tools/aggregate-probe`) дала однозначну на вигляд картину:

```
1. лише tap + output (як AudioCap):  ✅ 187 колбеків
2. input + output, main=output:      ❌ 0
3. input + output, main=input:       ❌ 0
4. лише input + tap (без output):    ❌ 0
```

Записаний тоді висновок: «BlackHole як віртуальний драйвер несумісний з process
tap в одному aggregate». Він **хибний**.

08.08, після того як на стенді видали дозвіл на мікрофон, той самий бінар на тому
самому залізі дав протилежний результат
(`docs/notes/evidence/aggregate-layout-probe-after-mic-grant.txt`):

```
C. input + output + tap в одному aggregate: ✅ 185 колбеків, буфери 2ch+2ch
```

Справжня причина нуля була в TCC, а не в BlackHole: **поки рішення про дозвіл на
мікрофон не ухвалене, `AudioDeviceCreateIOProcIDWithBlock` не повертається взагалі**.
`sample` на зависаючому процесі показує, де саме:

```
AudioEngine.startIO → AudioDeviceCreateIOProcIDWithBlock
  → HALC_ProxyIOContext::_TellServerAboutStreamUsage
    → mach_msg2_trap        ← стоїть тут нескінченно
```

Три наслідки, і всі троє — про продукт, а не про стенд:

1. **Архітектура підтверджена, а не спростована.** Мікрофон і tap справді
   працюють в одному aggregate (§2). Головний аргумент про синхронність вистояв.
2. **Знайдено реальний баг:** `start()` викликається з main actor, тож
   заблокований CoreAudio-виклик підвішує menu bar намертво — без діалогу на
   екрані і без способу вийти. Виправлено двома шарами: застосунок питає дозвіл
   мікрофона **до** того, як движок торкається CoreAudio (`STLTHRecorderApp`), а
   сам движок бере налаштування під дедлайн (`AudioEngine.bringUpAggregate`) і
   ніколи не блокує викликача довше 4 с.
3. **Методологічний урок.** «Змінна, яку я не контролюю» (стан TCC) виглядала як
   властивість коду. Правильна проба мала б спершу перевіряти, чи взагалі
   ухвалене рішення про дозвіл, — і лише потім перебирати розкладки aggregate.

## 3c. Tap не тікає в тиші — і це ламало критерій №4

Той самий день дав ще одну знахідку, цього разу з чистого спостереження: запис
8 секунд у повній тиші давав файл на **0 семплів**.

Причина не в помилці, а в природі process tap. Проба
(`Tools/running-probe`) показала точну поведінку, і вона несиметрична:

| Фаза | `DeviceIsRunning` | Колбеки |
|---|---|---|
| Нічого ще не грало | `false` | **0** |
| Грає звук | `true` | 94/с |
| Звук зупинили, 40 с тиші | `true` | **94/с** |

Тобто tap **не починає** віддавати буфери, поки якийсь процес не заграє — але
щойно почав, тікає безперервно, і тиша йде повноцінними нульовими буферами.
Пастка саме в першій фазі: якщо зустріч почалася раніше, ніж хтось заговорив,
для обліку її початку просто не існувало — таймлайн будувався виключно з
проміжків *між* буферами.

Для ТЗ це прямий удар по критерію №4 («10 хвилин mute не зсувають таймлайн»):
якщо клієнт замовкає, системний канал перестає тікати, і `system.caf` виходить
коротшим за `mic.caf` рівно на довжину паузи.

**Виправлено:** `TimelineAccountant` тепер прив'язується до власних міток часу
сесії — `start(at:)` на старті і `frames(toReach:)` на стопі. Довжину файлу
визначає тривалість сесії, а не останній буфер, який випадково прилетів.

| Сценарій (8–10 с) | До | Після |
|---|---|---|
| Повна тиша | 0 семплів | 384 884 семпли (8.018 с) |
| Звук лише в середині | обрізано з обох боків | 480 953 семпли (10.020 с), обидва треки рівні |

Побічний висновок, який варто пам'ятати: «нуль колбеків» сам по собі — **не**
ознака несправності. Тому детектор аварійного режиму при старті спирається лише
на таймаут налаштування, а не на відсутність колбеків: інакше кожна зустріч, що
починається з тиші, тихо деградувала б у гірший режим захоплення.

**А от watchdog під час запису ця сама проба зробила можливим.** Оскільки потік,
раз почавшись, не зупиняється, справжній збій має характерну підпис: пристрій
звітує `DeviceIsRunning = true`, а колбеки не йдуть. Саме ця пара умов, а не
голий лічильник, і стала критерієм перезапуску графа (§ `AudioEngine.watchdog`).
План вимагав «немає колбеків 3 с → перезапуск» — у такому вигляді це смикало б
запис на кожній паузі; з передумовою «потік уже стартував і пристрій каже, що
працює» те саме правило стає коректним.

## 4. Обмеження стенда

Розробка ведеться на **орендованому хмарному Mac mini M1** (flow.swiss, macOS 26.6).

Що це означає для довіри до результатів:

- 🚧 На стенді **немає фізичного мікрофона** — мікрофонний тракт тестується через
  BlackHole (loopback). BlackHole — **лише дев-залежність**, у продукті
  віртуальних драйверів немає (вимога F-2).
- 🚧 Хмарний мак не відтворює фізичні clock domains (Bluetooth-навушники) —
  найважчий випадок для синхронності. Мітигація: синхронність гарантується
  архітектурою (§2), а не вимірюванням; за наявності фізичного Apple Silicon
  перед здачею проганяється smoke-тест.
- GUI-сесія має лишатися живою (VNC), інакше зникають аудіопристрої і не
  показуються TCC-діалоги.
- **Дозволи TCC належать Terminal, а не sshd.** Процес, запущений по SSH, отримує
  колбеки, але буфери приходять цифровою тишею — жодної помилки, просто нулі.
  Тому всі прогони, де важливий *зміст* (drift-звіт, приймальні тести), робляться
  з Terminal на VNC-екрані; по SSH перевіряється лише те, чи взагалі йде потік.
  Це коштувало кількох годин хибних висновків, поки не звірили `TCC.db`:
  `kTCCServiceAudioCapture | com.apple.Terminal | allow`.

## 5. Дозволи (TCC) без приватних API

`NSAudioCaptureUsageDescription` в Info.plist — обовʼязковий ключ для промпту
про запис системного аудіо (в дропдауні Xcode його немає, вписується вручну).

Публічного API, щоб **прочитати** статус цього дозволу, не існує. AudioCap
розвʼязує це приватним TCC SPI (`TCCAccessPreflight` / `TCCAccessRequest` через
`dlopen`). Ми свідомо **не тягнемо приватний API у продукт**: це ризик на ревʼю
і при оновленнях ОС. Натомість стан виводиться з фактичної спроби створити tap.

🚧 *Фінальне рішення підтверджується в Task 10.*

## 7. Тестова стратегія

1. **Юніт (без аудіозаліза, у CI):** таймлайн, `meta.json`, state machine, session store.
   Фреймворк — **swift-testing**, а не XCTest: XCTest постачається лише всередині
   Xcode, тоді як swift-testing працює на чистих Command Line Tools. Це дозволило
   вести TDD ще до встановлення Xcode на стенді.
2. **Інтеграційні на стенді:** BlackHole-loopback як «мікрофон», реальний Zoom /
   Google Meet, `drift_check.py` з числовим звітом.
3. **Приймальна матриця** в README + нічний soak-тест (2+ год).

Drift-інструменти самі покриті тестом на синтетичному аудіо
(`Tools/selftest_drift.py`): вимірювач перевіряється на відомих зсувах
(0 / 150 / 400 мс) — щоб числам у звіті можна було довіряти.
Виміряна точність інструменту: **±3 мс** при порозі 300 мс.

## 8. Що б робив далі

За спаданням віддачі, з чесним поділом на «знаю, що треба» і «треба спершу виміряти».

**1. Перевірити на Bluetooth-навушниках — це єдиний неперевірений важкий випадок.**
Хмарний стенд не має ані фізичного мікрофона, ані пристрою з власним clock domain.
AirPods — саме той сценарій, де синхронність каналів перевіряється по-справжньому:
власний годинник, змінна затримка, перепідключення посеред зустрічі. Архітектура
(§2) має це закривати через `kAudioSubDeviceDriftCompensationKey`, і виміряні
+6.4 мс/год це підтверджують — але на BlackHole, а не на реальному радіотракті.
Це перше, що я б зробив, отримавши фізичний Mac.

**2. Визначитися з аварійним режимом `split-clock`.** Зараз він реалізований як
запобіжник на випадок, коли aggregate з мікрофоном не піднімається за 4 секунди.
Але жодного разу не спрацював на стенді — тобто його дрейф не виміряний. Незміряний
шлях, який мовчки послаблює головну гарантію продукту, гірший за його відсутність.
Треба або відтворити умови й зміряти дрейф у цьому режимі, або прибрати його,
лишивши чесну помилку «мікрофон недоступний».

**3. Watchdog за станом пристрою, а не за лічильником колбеків.** План передбачав
«немає колбеків 3 секунди → перезапустити захоплення». Стенд показав, що це хибний
критерій: tap мовчить у тиші за побудовою (§3c), тож такий watchdog смикав би запис
на кожній паузі в розмові. Правильна ознака — опитувати
`kAudioDevicePropertyDeviceIsRunning` на власному aggregate; спершу перевірити, що
ця властивість лишається `true` у тиші.

**4. Нотаризація.** Ad-hoc підпис змушує користувача робити правий клік → Open при
першому запуску. Для продукту, який ставить радник самостійно, це зайвий бар'єр і
зайвий привід засумніватися в безпеці. З обліковим записом Apple Developer Program
це знімається одним кроком у `release.sh`.

**5. Діагностичний пакет.** Коли в радника «не записалося», зараз немає чого
попросити. Пункт меню, що складає `meta.json`, останні рядки `OSLog` і поточну
конфігурацію аудіопристроїв у zip — окупається з першого ж інциденту. Особливо
враховуючи, що половина проблем тут виявилася станом TCC, а не кодом.

**6. Шифрування записів на диску.** Це розмови про особисті фінанси. Зараз файли
лежать відкритим LPCM у `Application Support`. FileVault покриває крадіжку ноутбука,
але не покриває доступ іншого процесу під тим самим користувачем. Мінімум —
обговорити з юристами STLTH строк зберігання і автовидалення.

**7. Що НЕ став би робити зараз:** переходити на per-process taps заради чистішого
клієнтського каналу. Виграш косметичний (менше сторонніх звуків), ціна — трекінг
аудіопроцесів, який ламається на перезапуску Zoom і не покриває живу зустріч у
кабінеті (§1). Замість цього — рекомендація Focus mode у README.

## 9. Що знайшов ручний прохід по інтерфейсу

Ядро було виміряне до мілісекунд — дрейф +6.4 мс/год, інваріант таймлайна з
нульовою похибкою, 51 тест зелений. А натиснути «Почати запис» було неможливо.

Робота руками на екрані дала **тринадцять дефектів** — вісім при першому проході
під основним користувачем і ще п'ять при встановленні на чисту машину. Жоден не
давав ані помилки компіляції, ані попередження, ані рядка в логах.

| # | Дефект | Чому не ловився |
|---|---|---|
| 1 | Кнопка дозволу вела в System Settings, де застосунку ще немає | macOS не показує застосунок у списку, доки той не запитав дозвіл жодного разу |
| 2 | `Почати запис` не відкривала нічого | `Window`-сцена не дивиться на `@State`-прапорець; відкривається лише через `openWindow(id:)` |
| 3 | «Замало місця» при 419 ГБ вільних | API вільного місця відповідають лише для наявних шляхів, а теки сесій на свіжому встановленні ще немає |
| 4 | Перший старт запису падав | tap створювався до того, як користувач відповів на діалог TCC |
| 5 | Українські тексти помилок ніколи не показувалися | `error.localizedDescription` читає `LocalizedError.errorDescription`, а не однойменну властивість типу |
| 6 | Список записів застигав на момент запуску | `MenuBarExtra` будує вміст один раз, тож `onAppear` спрацьовує єдиний раз |
| 7 | Діалоги дозволів відкривалися за чужими вікнами | menu bar agent ніколи не є активним застосунком |
| 8 | Іконка запису бурштинова, а не червона | `.multicolor` малює `record.circle.fill` бурштиновим — і він зливався з помаранчевим системним індикатором мікрофона |

Наступні п'ять вилізли лише тоді, коли застосунок ставив **окремий звичайний
користувач** — сценарій, який неможливо зімітувати з адмінського акаунта:

| # | Дефект | Чому не ловився |
|---|---|---|
| 9 | README вів у `/Applications`, а туди звичайний користувач писати не може | адміністратор перетягує туди мовчки і діалога пароля не бачить ніколи — а ТЗ вимагає встановлення **без** адмінських прав |
| 10 | «Замало місця» вдруге, тепер при 412 ГБ вільних | `volumeAvailableCapacityForImportantUsage` почав повертати 0, і цей нуль приймався як вимірювання, а не як «не знаю» |
| 11 | Індикатор системного аудіо не змінювався ніколи | `noteSystemAudioResult` існував і не викликався нізвідки — метод був написаний і забутий |
| 12 | Автозапуск вимкнений за замовчуванням | ТЗ описує продукт як agent з «автозапуском при вході в систему (перемикається)» — перемикач існує, щоб **вимкнути**; до того ж без автозапуску не виконується критерій №5 |
| 13 | Стан дозволу на системне аудіо забувався при перезапуску | тримався лише в пам'яті, тож застосунок писав «не запитано» тому, хто видав дозвіл місяць тому |

**Десять із тринадцяти робили продукт непридатним саме для нового користувача** —
тобто для того сценарію, який і перевіряє критерій приймання №5.

Дефект №10 заслуговує окремої уваги: це **повторна поява вже виправленої вади,
з іншої причини**. Перше виправлення навчило гард ходити вгору по дереву тек, але
лишило довіру до нуля від системного API. Спіймали його регресійні тести,
написані вранці під першу версію бага — той рідкісний випадок, коли тест окупився
за півдня.

Спільна риса всіх восьми: код робив рівно те, що написано. Помилка була не в
поведінці програми, а в тому, що бачить людина. Три останні знайшов не я, а
Володимир, просто дивлячись на екран.

**Висновок для тестової стратегії (§7):** UI-шар не покривається автотестами
взагалі, і жодне збільшення покриття ядра цього не змінює. Єдиний спосіб — ручний
прохід сценарієм нового користувача, на машині з невиданими дозволами. Це варто
робити перед кожним релізом, а не одноразово.

Окремо: **ad-hoc підпис змінює cdhash при кожній перезбірці**, тож macOS вважає
застосунок новим і скидає дозволи. На розробці це дратує, але дає безкоштовний
доступ до стану «перший запуск» — саме він і виявив половину списку вище.

## 10. Транскрибація: скільки вона насправді помиляється

Бонусний шар P5. Спершу вона існувала як скрипт, який я запускав руками, — тобто
для користувача продукту її не існувало. Тепер це пункт меню на сесії
(«Транскрибувати» в «Останні записи»), а результат лягає в `transcript.md` поруч
із аудіо.

**Атрибуція реплік не вгадується.** Більшість пайплайнів витрачає на це окрему
модель діаризації з власною похибкою. Тут вона не потрібна: `mic.caf` — це завжди
радник, `system.caf` — завжди співрозмовник. Те, що зазвичай є задачею, тут є
властивістю запису.

### Виміряна якість

Проблема вимірювання: щоб порахувати word error rate, потрібна мова з наперед
відомим текстом, а жодна реальна зустріч її не має. Тому еталон промовляє системний
голос, і далі той самий запис міряється двічі — як є, і після стиснення до
бітрейту зустрічі (`Tools/transcription-quality.sh`).

| Модель | Розмір | WER | Година сесії, на канал |
|---|---|---|---|
| `ggml-medium-q5_0` | 519 МБ | **3.1 %** | ~17 хв |
| `ggml-small-q5_1` | 184 МБ | 9.4 % | ~8 хв |

**Обрано medium.** Транскрибація — пакетна робота після зустрічі, її ніхто не
чекає в реальному часі, тож утричі менше помилок варті вдвічі більшого часу.
Small лишається запасним для машин, де є лише він.

### Що з'ясувалося несподівано

**Кодек зустрічі не погіршує розпізнавання.** Я очікував, що канал клієнта буде
гіршим за канал радника саме через мережеве стиснення, — і в транскрипті реального
Meet-дзвінка так і виглядало. Але вимірювання показало **однаковий WER** до і після
стиснення до 24 кбіт/с, на обох моделях.

Отже гіршу якість клієнтського каналу дає не бітрейт, а сам матеріал: жива
спонтанна мова проти чистої дикторської. Це змінює висновок, який я був зробив
уранці з вигляду транскрипта, — і показує, чому враження від тексту не замінює
вимірювання.

### Живий голос крізь реальний дзвінок

Синтезований еталон дав 3.1 %. Володимир прочитав той самий за складністю текст —
145 слів із відсотками й термінологією — у Zoom з Windows, і канал клієнта записав
його як на справжній зустрічі.

| Вимір | WER |
|---|---|
| Перший прогін, як є | **73.8 %** |
| Той самий запис із придушенням нерозмовних токенів | **26.2 %** |
| Він само, без числових слів | **19.2 %** |

Три числа, і різниця між ними — це три різні речі.

**Стрибок 73.8 → 26.2 — не покращення метрики, а знайдений баг продукту.** Модель
дописала у хвіст запису «[Режисер Микола Носок]» двадцять два рази: 75 вигаданих
слів проти 145 сказаних. Зустріч здебільшого складається з тиші, а whisper тишу
**заповнює вигадкою**. Транскрипт реальної години був би засмічений так, що
аналітичний пайплайн отримав би сміття замість розмови.

Виправлено там, де треба — у движку: `--suppress-nst` і поріг тиші 0.8. Фільтрувати
дужки постфактум було б косметикою: текст виглядав би чистим, але хвилини обчислень
однаково згорали б на розпізнавання тиші.

**Різниця 26.2 → 19.2 — не помилка, а формат.** Модель пише «60 %» там, де диктор
сказав «шістдесят відсотків». Для WER це помилка, для пайплайну — ні. Тому
`Tools/wer.py` рахує обидва числа.

**Решта 19.2 % — справжні помилки розпізнавання:** «петфель» замість «портфель»,
«воризонту» замість «горизонту», «орієнтер» замість «орієнтир». Тобто на живій
українській мові крізь мережу модель помиляється приблизно в кожному п'ятому слові —
вшестеро гірше, ніж на синтетичному еталоні.

Це і є чесна відповідь на питання «чи якісно транскрибує». Для пошуку по змісту й
виявлення тем — придатно. Для цитування клієнта дослівно — ні.

### Як зробити краще: що перевірено, а що ні

Питання «чи це проблема всіх таких застосунків» має конкретну відповідь: **ні, це
проблема української мови в малій моделі**. Whisper тренувався переважно на
англійській, і на ній medium дає приблизно 5–8 % на розмовній мові — утричі краще
за наші 26 %.

Перевірено на тому самому записі живого голосу:

| Що спробували | WER | Без чисел | Година, на канал |
|---|---|---|---|
| `small-q5_1` | 89.0 % | 92.0 % | ~5 хв |
| `medium-q5_0` | 26.2 % | 19.2 % | ~17 хв |
| `medium` + підказка з фінансовою лексикою | 29.0 % | 23.2 % | ~17 хв |
| **`large-v3-turbo-q5_0`** | **21.4 %** | **14.4 %** | **~9 хв** |

**Turbo виграє за обома осями одночасно** — точніший і вдвічі швидший за medium за
тридцять зайвих мегабайтів. Тут немає компромісу, який треба зважувати, тож він
став типовою моделлю.

**Small прибраний зі списку взагалі.** 89 % — це не транскрибація, а вигадування:
79 сфабрикованих слів проти 145 сказаних, і `--suppress-nst` його не рятує.
Запасний варіант, що тихо продукує фікцію, гірший за чесне «встановіть таку модель».

**Підказка з термінологією не спрацювала** — стало гірше на 3 пункти. Гіпотеза була
розумна: підказати моделі «портфель, облігації, диверсифікація», щоб вона не чула
«петфель». На практиці підказка додала вставок. Записую як перевірену і відкинуту,
щоб наступний не витрачав на неї час.

**Чого ще не пробували:** `large-v3` без turbo (утричі повільніший, виграш
неочевидний; з 1.3.0 саме вона відвантажується, але WER на цьому стенді не міряно
— див. §13), нормалізація гучності перед розпізнаванням, справжній VAD із
silero-моделлю замість порогу тиші, донавчання на українській фінансовій мові.
Останнє дало б найбільше, але потребує розмічених даних.

**Чого робити не можна:** віддати аудіо в хмарний API. Це зняло б проблему одним
кроком — але прямо суперечить вимозі ТЗ, що записи не залишають мак радника.

### VAD: не давати моделі тишу взагалі

`--suppress-nst` виявився недостатнім. Транскрипт реальної сесії закінчувався так:

```
[00:02:10] Дякую за перегляд!
[00:02:40] Дякую за перегляд!
[00:03:10] Дякую за перегляд!
[00:03:40] Дякую за перегляд!
```

Це не службовий токен, який можна придушити прапорцем, — це **правдоподібне
речення, яке модель вигадує з тиші**. Whisper влаштований так, що на вхідному вікні
завжди щось декодує; дай йому мовчання — отримаєш галюцинацію.

Рішення — не фільтрувати результат, а не подавати тишу на вхід: VAD-модель silero
(864 КБ) заздалегідь ріже запис на ділянки з мовленням.

| | Без VAD | З VAD |
|---|---|---|
| WER | 21.4 % | **16.6 %** |
| Без чисел | 14.4 % | **8.8 %** |
| Вставок (галюцинацій) | 9 | **1** |
| Час на 150 с аудіо | 22.5 с | **12.0 с** |

Виграш за всіма осями одночасно, і причина одна: **зустріч здебільшого складається
з тиші**, а тепер вона не витрачає ані обчислень, ані якості.

Підсумкове чесне число для живої української мови крізь дзвінок — **8.8 %** без
урахування формату чисел. Це вже придатно не лише для пошуку тем, а й для роботи з
цитатами з обережністю.

> **Примітка від 04.09.2026.** Усі числа в цьому розділі виміряні на
> `ggml-large-v3-turbo-q5_0`. З 1.3.0 типова модель — `ggml-large-v3-q5_0`, і її WER
> на живій українській **не міряно**: без Mac і без живого запису переміряти
> неможливо. 8.8 % лишається тут як історія вимірювання попередньої моделі, а не як
> характеристика того, що відвантажується зараз. Чому замінили — §13.

### Чого ці числа НЕ доводять

Еталон промовляє синтезований голос, а він розпізнається легше за людський. Тому
3.1 % — це **оцінка зверху**, стеля можливого, а не якість на реальній зустрічі.
Щоб отримати чесне число для живої мови, потрібен запис людини з наперед відомим
текстом; на цьому стенді, де немає навіть мікрофона, зробити його неможливо.

Так само не виміряні: споживання пам'яті на годинній сесії і поведінка на кількох
мовах у межах одної зустрічі.

## 11. Виявлення зустрічі без доступу до застосунків

Розділ 0 ТЗ називає причину, з якої продукт узагалі існує: «хтось просто забуває
увімкнути запис, і зустріч втрачається безповоротно». Записувач, що покладається на
дисциплінованість радника, цієї проблеми не вирішує.

### Чому не браузер і не назви процесів

| Підхід | Чому не він |
|---|---|
| Читати вкладки браузера | Потрібен дозвіл на Apple Events і діалог про скриптування — у продукті про приватні фінанси це виглядає гірше за саму задачу |
| Звірятися з назвами процесів | Ламається при кожному перейменуванні, не покриває вебклієнти, вимагає списку під кожен застосунок |

Але зустріч має ознаку, якої **жоден застосунок для дзвінків не може уникнути**:
щось тримає мікрофон відкритим. CoreAudio повідомляє це по процесах
(`kAudioProcessPropertyIsRunningInput`) починаючи з macOS 14.4 — тобто на тій самій
версії, яку вимагає tap. Проба `Tools/meeting-probe` підтвердила одразу:

```
[11:01:28] мікрофон тримають: zoom.us [us.zoom.xos]
```

Один механізм покриває Zoom, Meet у Chrome, Teams, Slack і Webex.

### Дві затримки, і обидві не косметичні

**П'ять секунд до оголошення.** Застосунки для дзвінків хапають мікрофон на мить,
коли відкриваєш їхні налаштування звуку. Нагадування на це привчило б ігнорувати
нагадування взагалі.

**Хвилина до завершення.** Перший живий прогін оголосив зустріч **двічі за 32
секунди**: mute у Zoom відпускає мікрофон, детектор прочитав це як кінець, а unmute —
як нову зустріч. На годинній розмові це означало б сповіщення після кожного mute.

Обидві величини взялися з поведінки на реальному дзвінку, а не з міркувань.

### Нагадування про зупинку важливіше за нагадування про старт

Забути ввімкнути — втратити зустріч. Забути вимкнути — продовжувати писати кімнату
після неї: наступний дзвінок радника, розмову з колегою. І все це ляже в сесію, чий
`meta.json` стверджує, що клієнт дав згоду на запис.

Перше нагадування рятує дані, друге рятує **від збору даних, на які згоди не було**.
Для продукту про особисті фінанси друге серйозніше.

### Чого застосунок не робить

Не вмикає і не вимикає запис сам. ТЗ формулює це прямо: «Рішення про старт приймає
радник — запис вмикається його дією, а не сам собою». Це стосується обох кінців
зустрічі: автостоп виглядав би зручним рівно до першої зустрічі, яку він обірве
посеред розмови.

### Пастка, на яку я наступив утретє за день

Виявлення спершу запускалося з `.task` на вмісті меню — а `MenuBarExtra` будує вміст
**ліниво, при першому кліку**. Детектор не працював, доки радник не відкриє меню, і
дозвіл на сповіщення не запитувався взагалі. Момент, заради якого функція існує, — це
рівно той, коли меню ніхто не відкривав.

Третій випадок за день, коли лінива ініціалізація SwiftUI зробила код мертвим без
жодного попередження (§9, дефекти 2 і 6). Правило, яке варто винести: **у menu bar
agent усе, що має працювати без участі користувача, ініціалізується поза ієрархією
view**.

## 12. Зведений файл: похідне, а не джерело правди

Два канали — це те, що потрібно аналітиці, і рівно те, чого не потрібно людині.
Щоб послухати зустріч, доводилося відкривати два файли й тримати їх у голові
паралельно. Тому поруч із доріжками тепер лягає `session.m4a`.

**Головне обмеження, яке треба тримати в голові:** зведення **похідне**. `mic.caf` і
`system.caf` лишаються недоторканими й далі є єдиним джерелом правди для пайплайну.
Помилка зведення не робить сесію невдалою, не блокує `stop()` і не підвішує UI — воно
будується у фоні вже після того, як сесія стала `completed`.

### Чому нативний AVFoundation, а не ffmpeg

Транскрибація може дозволити собі зовнішню залежність: вона опційна, і застосунок
чесно каже, якою командою її додати. Зведення такої розкоші не має — це частина
основного флоу, вона мусить працювати з коробки, на щойно встановленому Mac, без
Homebrew.

`AVAudioEngine` в offline-режимі теж не знадобився: немає ні реального часу, ні графа
ефектів. Читання через `AVAudioFile` блоками по 48000 кадрів, складання в пам'яті,
запис через `AVAudioFile(forWriting:settings:)` з `kAudioFormatMPEG4AAC`. Менше стану —
менше місць, де щось піде не так.

### Чому AAC, а не LPCM

Сесія вже важить ~16.5 МБ за хвилину. Стерео LPCM додало б ще ~11 МБ/хв — тобто
файл **для прослуховування** здорожчив би зберігання майже вдвічі. AAC 96 кбіт/с дає
~43 МБ на годину замість ~700 МБ. Для мови цього більш ніж достатньо, а вихідні
доріжки лишаються без втрат.

### Чому 85/15, а не жорстке L/R

Повне розділення — найлегша для розбору картина: миттєво чути, хто кого перебив.
Але година жорсткого панорамування втомлює, а на одній колонці один зі
співрозмовників зникає повністю. При 85/15 розділення лишається очевидним, і обидва
голоси переживають зведення в моно. Змінюється однією константою.

### Запас гучності — не через суму

Спокуслива логіка «дві доріжки складаються, отже може клiпувати» тут неправильна:
при такому панорамуванні перекриття невелике. Справжня причина запасу в іншому —
**AAC дає міжсемплові викиди вище 0 dBFS при декодуванні**. Мікс, що впирається
рівно в 1.0, повертається з-за кодека вищим і загортається. Тому 0.8 перед
кодуванням, і тест на двох джерелах повної шкали.

### Вирівнювання не робиться — і не потрібне

Обидві доріжки пишуться одним IO-колбеком одного aggregate device, а всі розриви вже
залиті тишею через `TimelineAccountant` (§3). Вони однакової довжини й вирівняні
посемплово. Тому зведення — просте складання з нульового кадру: ані кроскореляції,
ані пошуку зсуву. Шукати тут зсув означало б лікувати проблему, яку архітектура
усунула.

### Пастка, яку легко проґавити

Сесія, перервана крахом, несе `data`-чанк розміру −1 (§3a). Apple-стек читає такий
файл мовчки — тобто зведення **вдалося б і виглядало нормальним**, просто обірваним.
Тому `CAFRepair.repairIfNeeded` викликається на обох доріжках **перед** зведенням,
завжди, а не лише під час відновлення.

### Що перевірено

Довжина в межах допуску (AAC додає priming/padding, точний збіг до семпла дав би лише
LPCM) · тиша-паддинг лишається на місці · сигнал лише в мікрофоні дає енергію ліворуч
· два джерела повної шкали не клiпують · повторний виклик ідемпотентний · відсутня
доріжка дає типізовану помилку · CAF з розміром −1 лікується дорогою.

На реальній сесії 223.306 с: зведення за 1.3 с, тривалість збіглася до мілісекунди,
0 семплів кліпінгу, співвідношення каналів 0.177 при заданих 0.15/0.85.

## 13. Автотранскрибація, видалення аудіо, large-v3 (1.3.0)

Три поведінки перенесено з Windows-версії того самого продукту. Нижче — не що
зроблено (це видно з коду), а розвилки і чому обрано саме так.

### Чому черга, а не паралель

Розпізнавання навантажує процесор приблизно стільки ж часу, скільки тривала
розмова, і то на кожну доріжку. Дві сесії поспіль запустили б два whisper
паралельно, обидва пішли б удвічі повільніше — на машині людини, яка щойно поклала
слухавку і, ймовірно, відкриває наступний дзвінок. Тому одна сесія за раз.

Windows робить це через `SemaphoreSlim(1,1)`. У Swift concurrency блокуючого
примітива, який безпечно тримати через `await`, немає, тож `SerialTaskQueue` — це
`actor`, який тримає хвіст ланцюжка задач: кожна нова робота `await`-ить попередню
й лише тоді стартує, у `Task.detached`, щоб хвилини роботи whisper не тримали ні
актор, ні виконавця того, хто поставив у чергу. Робота, що кинула помилку,
звільняє ланцюжок так само, як успішна — помилку бачить лише її власний викликач.
Тест `jobsNeverOverlap` тримає першу роботу на континуації й перевіряє, що друга
не почалася; `failureReleasesQueue` — що після помилки черга не зависла.

### Чому один конвеєр для авто й ручного шляху

`TranscriptionPipeline.run` — єдина точка, як `RunAsync` у Windows. Інакше та сама
увімкнена опція (передусім видалення аудіо) поводилася б по-різному залежно від
того, як людина запустила розпізнавання — з меню чи автоматично, — і пояснити це
було б нічим. Різниця між шляхами лише в тому, що бачить людина: ручний показує
транскрипт у Finder або алерт з помилкою; автоматичний логує й мовчить, бо помилка
не робить сесію невдалою — аудіо на місці, транскрипт можна зібрати ще раз.

### Чому видаляти тільки за наявності мови — і тільки після зведення

Видалення доріжок — єдине місце в продукті, де він знищує записи людини, тому
рішення винесено в чисту функцію `SessionStore.mayRemoveAudio(enabled:hadSpeech:)`
і перевірено з обох боків. Умова про мову — не формальність: порожній транскрипт
означає «розпізнавання нічого не знайшло», і видалити аудіо саме в цей момент —
найгірший можливий результат: запису немає, а замість нього файл із написом
«мовлення не розпізнано». Для цього `Transcriber.transcribe` тепер повертає
`TranscriptResult { url, hadSpeech }` замість голого URL — Windows тримає це в
`LastRunHadSpeech`, статичний метод у Swift стану тримати не може.

Другий запобіжник — не з Windows. Зведення і транскрибація стартують паралельно
після зупинки запису; на дуже короткому записі whisper може закінчити раніше, ніж
AAC-кодер, і видалити доріжки з-під нього означало б лишити сесію без жодної
слухабельної копії. Тому, поки зведення увімкнене, аудіо йде лише коли
`session.m4a` уже існує. Рішення читається *після* транскрибації, не в момент
постановки в чергу: whisper працює хвилини, і перемикач, який людина змінила за цей
час, має враховуватися.

Порядок жорсткий: спершу транскрипт на диск, потім видалення. Помилка видалення
проковтується (`try?`, як у `noteMix`) і не забирає з собою транскрипт. Факт пишеться
в `meta.json` як `audioRemovedAt` — і лише коли справді щось звільнено: порожня
тека це не «аудіо видалили», і позначати її так було б брехнею. Меню сесії без
доріжок не пропонує ні зведення, ні транскрибацію — це не поломка, а наслідок
увімкненої опції, і воно так і каже.

Опція вимкнена за замовчуванням: економія реальна (~990 МБ доріжок проти ~43 МБ
зведення на годину), але втрата безповоротна. Разом із вимкненим зведенням від
сесії лишається сам текст — налаштування кажуть це прямо.

### Чому large-v3 замість turbo, і що з числом 8.8 %

Turbo вдвічі швидший, бо його декодер здистильований із 32 шарів до 4 — а саме
декодер відповідає за те, щоб токени складалися в осмислену послідовність.
Windows-збірка побачила це на українській прямо: turbo давав «Тораз глянемо» там,
де повна модель чує «Та розглянемо», і уламки замість слів. Транскрибація — фонова
робота після розмови, тож удвічі більше часу коштує менше, ніж спотворені репліки.

**Чесно про число.** 8.8 % WER у §10 виміряно на turbo. На цьому стенді немає ні
Mac, ні живого запису, щоб переміряти large-v3, тож число з README знято, а в §10
лишено з приміткою. Це рішення на основі чужого спостереження, не власного виміру,
і так і записано. `Tools/wer-live.sh` лишається інструкцією для того, хто переміряє.

Порядок заміни має значення: turbo прибирається **тільки після** того, як новий файл
завантажений і його digest збігся (`ModelInstaller.removeSuperseded` викликається
після циклу завантаження, не всередині; помилка або скасування минають його) —
інакше зірване завантаження лишило б людину без жодної робочої моделі. До
перезавантаження turbo лишається кандидатом у `Transcriber.modelCandidates`, тож
машина з 1.2.0 продовжує розпізнавати на ній; налаштування пояснюють, чому просять
завантажити ще гігабайт.

Пінінг нової моделі: 1 081 140 203 Б, sha256 `d75795ec…98ad1` — перевірено повним
завантаженням файлу і хешуванням, збігається з LFS-метаданими HuggingFace. Windows
пінить лише розмір, тож звідти взяти було нічого.

### Що перевірено і чим

Розробка йшла на Windows без жодного Mac. Тому:

- **Ядро** — `swift test` на `macos-15` у CI: 100+ тестів, зокрема рішення про
  видалення (увімкнено × є мова), серіалізація черги, `audioRemovedAt` у round-trip
  і декодування старого `meta.json` без поля, `removeAudio` (звільнені байти, похідні
  файли на місці), прибирання turbo лише після успішної заміни й ніколи після
  помилки чи скасування.
- **SwiftUI-шар** — джоба `app-build` у CI збирає й лінкує весь бандл тим самим
  шляхом, що `release.sh` (`scripts/build-app.sh release`). До 1.3.0 на push
  компілювалося лише ядро, і помилка в `App/Sources` доїхала б до DMG непоміченою.
- **Справжній whisper** — `.github/workflows/e2e-transcription.yml` (ручний запуск):
  завантаження обох моделей через `ModelInstaller.httpFetch` з перевіркою digest і
  прибиранням підкладеного turbo, синтезована мова через `say -v Lesya`, транскрибація
  large-v3 зібраним whisper-cli v1.9.2, видалення доріжок і `audioRemovedAt`, тиха
  сесія лишає аудіо, дві сесії в черзі не перекриваються. Прогін 04.09.2026 —
  `docs/notes/evidence/e2e-large-v3-runner.txt`:

  | Крок | Результат |
  |---|---|
  | Завантаження 1,01 ГБ через `httpFetch` | 119 с, обидва digest збіглися, підкладений turbo прибрано після |
  | large-v3, два треки по 10 с, CPU ранера без Metal | 184 с (VM на 3 ядра — це число про ранер, не про Mac радника) |
  | Транскрипт синтезованої фрази | слово в слово: «Доброго дня! Сьогодні ми обговоримо структуру вашого портфеля та цілі на найближчі три роки.» |
  | Тиша 10 с з VAD | `hadSpeech == false`, доріжки на місці, `audioRemovedAt` відсутній |
  | Дві сесії в черзі | `A start, A end, B start, B end` |

  Збіг слово в слово — на **синтезованому** голосі, тобто стеля, а не якість на
  живій зустрічі (§10 пояснює різницю: на живому голосі turbo давав 16.6 % проти
  3.1 % на синтезі). Але це доводить, що файл моделі відкривається зібраним
  whisper-cli, JSON має очікувану форму, а український текст модель віддає, а не
  вигадує.

  Пастка, на яку цей воркфлоу наступив першим же прогоном: `make … | tee` під
  типовою оболонкою GitHub Actions не має `pipefail`, і джоба з харнесом, що не
  злінкувався, була зеленою. Тепер крок іде під `shell: bash` (pipefail
  увімкнений) і окремий крок вимагає в лозі останній рядок харнеса.

**Що НЕ перевірено:** поведінка меню і налаштувань очима (ніхто не клікав), запис
на живому Mac з 1.3.0, WER large-v3 на живій українській.
